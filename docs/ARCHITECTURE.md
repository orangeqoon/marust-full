> **位置づけ**: marust の構造の正本。用語は `GLOSSARY.md`、重い判断は `docs/adr/`（0007 が 0005 の「核は画面も窓口も持たない」「一層目は本体のコード」を置き換える）、設計の詰めは `docs/GRILL-2026-10-12.md` に従う。

## 0. ユーザー決定

基本方針。設計の進展に伴う詳細な決定は GRILL（`docs/GRILL-2026-10-12.md`）および ADR（`docs/adr/` 0001〜0006）を正本とする。

- **名前**: marust（まるスト）。
- **核の役割**: 配信エンジンと複数のサイトをつなぐ分かれ道。サイトの追加、配信先を OBS に作ること、配信開始で全部を出すこと、全部止めること（ADR 0002）。それに加え、変わりにくいもの（窓口の土台・ペアリング・承認・プラグインの読み込み・トレイ・画面の入れ物）も核（ADR 0007）。
- **4 つの層**: 核と、セットの中の一層目（基本）・二層目（管理）・三層目（改善）。層の名前は ADR 0005。一層目は本体のコードではない（ADR 0007）。
- **配信エンジン**: marust 専用に fork した obs-multi-rtmp（id `obs-local`）と OBS のメイン出力。OBS 上では操作せず、marust から操作する（ADR 0002, 0004）。marust が落ちても配信エンジンは送出を続ける。
- **常駐ツール**: YouTube 12h 切替・ニコ生枠取り・配信監視・同接記録などの常駐ツールは飲み込まない。各ツールの公開口と通信してつなぐ。
- **秘密の守り**: 金庫にだけ保存、画面は末尾 4 文字、出口で伏せるの 3 つ。事故から守り、悪意からは守らない（ADR 0006）。
- **画面**: ドック（dockview）でパネルを自由に配置・タブ化・切り離しできる。
- **全部止める**: 1 クリックですぐ止まる。メイン出力も含めて止める。非常停止はこれに吸収（ADR 0002）。
- **モード**: 核にモードは無く最初から live。モードは作者用プラグイン（三層目）にする（ADR 0003）。

## 1. 原則

1. **核は変わらないもの。** 配信の分かれ道に加え、窓口の土台・ペアリング・承認・プラグインの読み込みと読み直し・トレイ・画面の入れ物を持つ。サイト固有の処理、ログイン、タイマー、カレンダー、題名の一斉送信、パネルの中身、言葉、ガイドはプラグインに置く。
2. **marust が落ちても配信は止まらない。** 映像の送出は配信エンジンが担う。marust は指示を出し、送信中の状態を読むだけ。
3. **配信エンジンを抽象化する。** 核は配信エンジンを `stream.engine` の役割として扱う。データや API に OBS 固有の名前を持ち込まない。
4. **照らし合わせ（Reconciliation）。** 起動や再接続のたびに実状態を読み直す。自分の記憶だけで配信を止めたり始めたりしない。外で起きた変更は受け入れ、巻き戻さない。
5. **送信中と配信中を分ける。** OBS が映像を送れている状態（`engineState`）と、サイトの上で配信が公開されている状態（`siteLive`）を分ける。核が知る「出た」は送信中だけ。配信中はログインを持つプラグインがあるときだけ扱う。
6. **秘密の守りは 3 つ。** 値は金庫にだけ置く。画面には末尾 4 文字だけ出す。ログ・エラー・診断・書き出し・窓口へ出る直前に金庫の値と同じ文字列を伏せる。プラグインは manifest で宣言した秘密を値のまま使える（ADR 0006）。
7. **核は核しか require しない。** フォルダ `host/core/` の中のコードは核の中だけを require する。一層目やプラグインを require しない。
8. **配信を実行するのは PC、操作する端末は問わない。** 映像のエンコードと送出は PC の配信エンジンだけ。スマホ等は操作・確認・通知の端末とする。

### 2.1 セットの置き場（D6）

先に見つかったものを使う（`host/core/set-dirs.js` の `resolveSetDirs`）。返す行は `{ dir, source: 'set', author, community }`。

| 順 | 置き場 | いつ |
| :--- | :--- | :--- |
| 1 | 環境変数 `MARUST_SET_DIR` | 複数はパスの区切り（Windows は `;`）。フォルダ名が `plugins-author` のものは作者用の印 |
| 2 | `build-info.json` の `setDirs` | 作者の build が書く。文字列か `{ dir, author, community }` |
| 3 | exe の横の `plugins/` | 配る版（`appRoot` が `resources/app`）で、1 と 2 が無いとき |
| 4 | ソース起動 | リポジトリの `plugins/`、隣の `../marust-plugins/plugins`（`community: true`）、`plugins-author` |

配る版で 1〜3 のどれも無いときは `{ from: 'none', dirs: [] }`。リポジトリの置き場は探さない。核だけで起動する。作者の版かは置き場の名前ではなく `isAuthorBuild(appRoot)`（`build-info.json` の `distribution === 'author'`、またはソース起動で `plugins-author` がある）で決める。

## 3. 4 つの層

marust は核と、セットの中の 3 つの分類でできている（ADR 0007。層の名前は ADR 0005）。公開版は核とセットで、セットの中に一層目・二層目と三層目の一部がある。

| 層 | フォルダ | 役割 | 主な内容 |
| :--- | :--- | :--- | :--- |
| **核**（変わらないもの） | `host/core/`、`host/layer1/`、`ui/` の入れ物 | 配信の分かれ道に加え、窓口の土台・ペアリング・承認・プラグインの読み込み・トレイ・画面の入れ物。サイトの名簿やパネルの中身は持たない。`host/core/` は核の中しか require しない | 配信先の一覧（ストリームキーは OBS の行にだけ置き、金庫には入れない）、配信開始（全部を出す）、全部止める（メイン出力を含む）、送信中の読み取り、合図（events）、配信エンジン（`engine/`）、窓口（`127.0.0.1:18770`）、枠・ペアリング・最低限の表示（`ui/`） |
| **一層目**（基本） | セットの中の layer1 一覧 | セットの中の「基本」。本体のコードではない | 画面の本体役（`plugins/ui-standard`、`kind: shell`）、サイトの名簿（`plugins/sites/*`）、テーマ 2 つ（`theme-default`、`theme-light-large`）、更新の確認（`update-check`）。CLI（`cli/`）は核でもプラグインでもない外の道具 |
| **二層目**（管理） | セットの中の layer2 一覧 | サイトへ書きにいく管理機能。`plugin-layers.json` の layer2 の一覧で決まる | 題名の一斉送信（`bulk-title`）、ホットキーの設定（`hotkeys`）、回線の余裕（`uplink-estimate`）、設定の書き出しと戻し（`backup`）、コメント送信（`comment-send`）、わんコメの橋（`chat-inlet`）、`kukulu-port`、`kukulu-sleep`、`set-youtube`、`site-login` |
| **三層目**（改善） | 一覧に無いセット、`plugins-author/`、`<STATE_DIR>/plugins` | 改善の層。自分で足したものと、セットのうち `community` の印が付いたものは常にここ | 一覧に無いセット（`ai-connect`、`session`、`diagnostics`、`notify-discord`、`signal-monitor`、`dev-shadow` など）、作者用（`plugins-author/`、`author-modes` 等。出どころは `set`）、自分で足したもの（出どころ `user`）。三層目は配信を始められない（`layer3-no-start`）、全部止めるを邪魔できない |

### 3.1 フォルダの境界
- `host/` の下のフォルダは `core/` と `layer1/` だけ。`host/layer1/` は核の一部（窓口・読み込み・つなぎ口）。名前は変えない（計画 C・D1）。
- `host/core/` のコードは核の中だけを require する（`test/l7-layers.test.js` が検証する）。
- 画面の中身（パネル・メニュー・言葉・案内）は `plugins/ui-standard/shell/`。`ui/` に残るのは枠（`hub.html`）・ペアリング・最低限の表示（`fallback.*`・`core-strings.js`）・`plugin-host`。
- プラグインは `host/` を require せず、渡された `ctx` を通して操作する。

## 4. 中心データ

### 4.1 配信先（Destination）

1 つのサイトへ映像を送る行き先。サーバーの URL とストリームキーの組。OBS の中では obs-multi-rtmp のターゲット 1 つか、OBS のメイン出力に当たる。

```text
Destination {
  id            "youtube-main"
  site          "youtube"                     … どのサイトか
  accountId     "youtube-main"                … どのアカウントか（秘密の名前: cookies.<accountId> 等）
  engine        { id: "obs-local", targetId } … どの配信エンジンの、どの出力か
  enabled       今日この配信先を使うか
  actual        { engineState, siteLive }     … 送信中と配信中
  keyTail       "••••1234" | "" | null        … 末尾 4 文字（入っていない="", OBS側にある=null）
}
```

- `keyKind`、`desired`、題名やカテゴリの `actual` は核に持たない（削除済み）。
- メイン出力は固定の配信先 id `obs-main` として扱う（エンジンは `obs-local`、特別なターゲット `main`）。
- **送信中**（`engineState`）と**配信中**（`siteLive`）を分ける:
  - 送信中: OBS が配信先のサーバーへ映像を送れている状態（`live` / `connecting` / `reconnecting` / `stopped`）。核が知る「出た」はこれだけ。
  - 配信中: サイトの上で配信が公開されている状態。サイトの API やログインを持つプラグインを入れたときだけ扱う。

### 4.2 セッション（Session）

題名の付いた配信の区間。**セッションは核には無い**（ADR 0002）。セッションやタイマーのプラグイン（`plugins/session/` など）が核の合図を受けて記録する。

- セッションプラグインは核の合図 `broadcast.started` でセッションを開始し、`broadcast.stopped` の `all: true` で終了する。
- 状態の保存はセッションプラグイン自身が行う（自分の dataDir の `session.json`）。
- タイマーや Google カレンダーなどのプラグインは、核の合図やセッションプラグインの合図を受けて動く。

## 5. プラグイン

核と一層目の外に足す機能のまとまり。二層目と三層目の機能はすべてプラグインとして動く。

### 5.1 動かし方
- プラグインはすべて同じプロセス（`runtime: "inproc"`）で動く。
- Safe-Runner が例外とタイムアウトを隔離する。

### 5.2 層ごとの違い
- 出どころは `source: 'set'`（セット。配る版・作者用・みんなのプラグイン）と `source: 'user'`（自分で足したもの）。同じ id はセットが勝つ。
- 何層目か: 自分で足したもの、およびセットのうち `community` の印が付いたものは常に三層目。ほかのセットは `host/layer1/plugin-layers.json` にあればその層、無ければ三層目。
- **三層目の制限**:
  - 配信を始める呼び出し（`broadcast.start`、`engine.start`、`destination.start`、`destination.setMain { use: true }`、`obs.streamControl({ action: 'start' })`）は `layer3-no-start` で断られる。配信を止める呼び出しは通る。
  - 「全部止める」を邪魔できない。全部止めるの最中は、どの層からも配信の開始が `stopping` で断られる。

### 5.3 manifest v2（例）

```json
{
  "id": "gcal",
  "name": "Google カレンダー記録",
  "version": "1.0.0",
  "manifestVersion": 2,
  "runtime": "inproc",
  "main": "index.js",
  "provides": ["session.recorder@1", "ui.panel@1"],
  "subscribes": ["session.*", "broadcast.*"],
  "secrets": ["google.oauth"],
  "timeouts": { "onEvent": 15000 },
  "tier": "advanced"
}
```

- manifest の `secrets` で宣言した秘密は、層に関わらず値のまま `ctx.secrets.get(name)` で使える（ADR 0006）。宣言の無い `set` は断られる。
- モードは核に無く、最初から live として動く。作者用プラグイン `author-modes` が有効なときだけモード切り替えが働く（ADR 0003）。

### 5.4 合図（イベント）

合図の外側の形は固定する。中身は `payload` に入る。

```text
{ name, version, id, occurredAt, source, correlationId, payload }
```

主な合図の一覧（`host/core/events.js` より）:

| 合図名 | 内容 |
| :--- | :--- |
| `broadcast.started` | 配信を開始した（1 つ以上の配信先が送信中になった） |
| `broadcast.stopped` | 配信を停止した（`all: true` は全部止めるによる停止） |
| `broadcast.result` | 配信開始・停止の成否結果 |
| `stream.starting` / `stream.started` | 個別配信先の送信準備・送信開始 |
| `stream.stopping` / `stream.stopped` | 個別配信先の送信停止中・停止完了 |
| `engine.target.changed` | 配信先ごとの送出状態の変化（OBS エンジンからの通知） |
| `engine.emergencyStop` | 全部止める（合図名は互換のため残る） |
| `destination.observed` | 配信先の実状態の観測 |
| `site.trouble` | サイトの困りごと（ログイン切れ、回数制限、通信不能など。配信は止めない） |
| `slot.acquired` | 自動枠取りで枠が確定・更新された |
| `slot.switching` | 自動枠取りの枠切り替えの開始と終了 |
| `session.started` / `paused` / `resumed` / `ended` / `retitled` | セッションプラグインが発行するセッション状態 |
| `chat.message` / `chat.sent` | コメント 1 件の受信 / 送信結果 |
| `auth.updated` | ログイン情報の更新（値は含めない） |
| `viewer.count` | 同接数 |
| `hotkey.result` | ホットキー押下の結果 |
| `feature.toggled` | 機能プラグインの有効/無効切替 |
| `signal.stateChanged` | 回線状態の変化 |

## 6. 配信エンジン（OBS エンジン）

### 6.1 役割の分担

| 配信エンジン（OBS の中） | marust |
| :--- | :--- |
| 配信先ごとの出力・エンコード共有・送出 | 何をどこへ配信するかを決める |
| 切断時の自動再接続 | 配信前チェック、枠の確保 |
| 状態の通知（`target_state_changed`） | 状態の表示、送信中の確認 |
| 設定の保存（`obs-multi-rtmp.json`） | 配信先の作成・編集・有効化・開始・停止の画面 |

通信は **obs-websocket の vendor request**（vendor 名 `obs-multi-rtmp`）。API は `streaming/obs-multi-rtmp/WEBSOCKET_API.md` が正本。

### 6.2 marust が落ちても配信し続ける
- 送出は OBS プロセスが行うため、marust が終了・クラッシュしても送出は続く。
- marust が再起動したときは、OBS から実状態を読み直して照らし合わせる。自分の記憶を理由に配信を止めたり始めたりしない（原則 4）。

### 6.3 配信開始の流れ
1. **配信前チェック**: エンジンの接続状態、各配信先の設定を確かめる。
   - 全体の error（OBS 未接続など）のときだけ配信全体を止める。
   - 配信先ごとの error は、その配信先 1 つを外して残りの配信先を出す。外した配信先は理由と「もう一度出す」を画面に出す。出せた分は巻き戻さない。
2. **送信開始**: 有効な配信先（メイン出力 `obs-main` を含む）へ順次送信を開始する。
3. **送信中の確認**: 送信中（`engineState` が live）になったことを確かめる。
4. **合図**: 1 つ以上の配信先が送信中になってから、合図「配信を始めた」（`broadcast.started`）を出す（決まったこと 11）。
5. だめだった配信先は、ほかを出したままキーを貼り直す・行を作り直すなどして、その 1 つだけを出すことができる。送信中の配信先は書き換えを鍵にする。

### 6.4 全部止める（broadcast.stopAll）
- 止め方は「全部止める」と「配信先を止める」の 2 つ（ADR 0002）。
- 非常停止は「全部止める」に一本化された。
- **メイン出力を含めて全部の配信先を止める**。
- 止まったかを配信エンジンに確かめてから結果を返す。
- 押し方は普通の 1 クリックですぐ止まる。長押しも赤の状態も無い。
- 押しまちがいは確認画面ではなく置き場所で防ぐ。「配信開始」と別の場所の別のボタンにする。
- 窓口の API は `broadcast.stopAll`（`engine.emergencyStop` は互換のため残り、内部で `broadcast.stopAll` を呼ぶ）。

## 7. セッションと Google カレンダー

### 7.1 セッションはプラグイン
**セッションは核には無い**（ADR 0002）。セッションプラグイン（`plugins/session/`）が核の合図を受けて記録する。
- 核の合図 `broadcast.started` で自動で開始し、`broadcast.stopped` の `all: true`（全部止める）で終了する。
- 保存先は自身の dataDir の `session.json`。

### 7.2 Google カレンダー記録
Google カレンダー記録もプラグインとして動く。
- タイマー（`session.controller`）と Google カレンダー（`session.recorder`）は別プラグインで、お互いを知らない。
- 現行の結合ルール（同じ題名で前回の終了から 10 分以内の再開なら同じ予定に結合）はプラグイン側で維持する。
- 秘密（`google.oauth`）は金庫から取得する。

## 8. 秘密の守りとログイン情報

### 8.1 秘密の守りは 3 つ（ADR 0006）
プラグインは marust と同じプロセスで動き、Windows の DPAPI は同じユーザーのプログラムなら解けるため、悪意のあるプラグインから秘密を守ることはできない。秘密の守りは事故の防止に合わせる。

1. **金庫にだけ置く**: API キー・Cookie・OBS のパスワード（ストリームキーは OBS の行にだけ置く）は Electron の safeStorage（Windows の DPAPI）で暗号化して保管する。
2. **画面は末尾 4 文字**: 画面には `••••1234`（12 文字未満なら `••••`）だけ出す。
3. **出口で自動で伏せる**: ログ・エラー・診断・書き出し・窓口・AI 接続へ出る直前に、金庫の値と同じ文字列を自動で伏せる（`***`）。

プラグインは manifest の `secrets` で宣言した秘密を、層に関わらず値のまま `ctx.secrets.get(name)` で使える。代理やプラグインどうしの秘密の分けは無い（ADR 0006）。宣言の無い `set` は事故防止のため断られる。

### 8.2 Chrome 連携
- Chrome のプロファイル（Cookie の DB）は直接読まない。
- ブラウザ拡張機能から Cookie を受け取り、金庫へ保管する。
- 画面とログにはサイト・件数・期限・更新時刻だけを出す。

## 9. コメント（わんコメとの連携）

- **コメントの受け取りはわんコメに任せきる**（決まったこと 27）。marust はコメントを受信しない。
- 二層目のコメントは「サイトへ送る」（`comment-send`）と「わんコメとの橋」（`chat-inlet`）だけ。
- コメント受信のプラグイン（`chat-*`）は三層目の作者用。

## 10. 常駐ツール（飲み込まない・つなぐ）

常駐ツール（YouTube 12h 切替・ニコ生枠取り・配信監視・同接記録）は飲み込まず、通信してつなぐ。marust は起動・停止・再起動を管理しない。

- **サイトの困りごと（`site.trouble`）**: 二層目の仕事（題名・コメント・枠）がサイトで失敗したときは、全サイト共通の合図 `site.trouble`（`{ site, job, kind, code, at }`）を出す。配信（送信中）は止めない。ホームに 1 行知らせる。一時的な失敗は自動でやり直す。

## 12. 画面と外部クライアント（一層目）

### 12.1 形
- **一層目の窓口**: `127.0.0.1:18770`（HTTP + WebSocket）。
- **Web UI**: 窓口が配信し、Electron ウィンドウはこれを開く。ブラウザや OBS ドックでも同じ Web UI を開ける。画面は窓口の API だけを使う。
- **CLI**: `cli/marust.js`。配信の確認・開始・「全部止める」（`stop-all`）などを行う。
- **モード**: 核にモードは無く、最初から live。モード管理は三層目の作者用プラグイン `author-modes` が担う。

### 12.2 窓口の安全
- WebSocket の Origin 確認（自分の Web UI・ペア済みの拡張だけ）。
- Host ヘッダー確認（`127.0.0.1:18770` / `localhost:18770` 以外は拒否）。
- 権限 3 段: read / write / emergency。外部クライアントはペアリングでトークンを受け取る。

### 12.3 画面のレイアウト（dockview）
- OBS Studio 風のドック構成。パネルを自由に配置・タブ化・切り離し可能。
- 1 パネル = 1 部品。プラグインのパネルは sandbox の iframe でドックに入る。

- 公開版は核・一層目・二層目と、三層目の一部（他の人のプラグインを入れる仕組みなど）で構成される。
- 作者用の機能（タイマー、カレンダー、モード管理など）は三層目の作者用プラグインとして維持される。

## 14. 設計上の決定事項

1. 非常停止は「全部止める」（`broadcast.stopAll`）に一本化。1 クリックでメイン出力も含めて止める（ADR 0002）。
2. 核はサイトの存在を知らず、配信先の一覧とストリームキーだけを管理する（ADR 0002, 0005）。
3. 秘密の守りは事故防止の 3 つに絞り、悪意への守り（プラグインどうしの分けや代理）は行わない（ADR 0006）。
4. コメント受信はわんコメに任せ、丸ストは送信と橋だけを担う（決まったこと 27）。

## 15. 将来の拡張（構想。今は作らない。意図を残す）

ここは**決定ではなく、設計上の逃げ道を残す理由の記録**。作るかどうかは、下の「見直すきっかけ」が来たときに改めて決める。

### 15.1 クラウドの配信エンジン（映像の多重化をクラウドで行う）
- **形**: PC の OBS（またはスマホ）→ 映像 1 本 → クラウドの配信エンジン → 各サイト。Core からは `stream.engine` の 1 つ（例: id `cloud-relay`）に見える。
- **意図**: ① 自宅の上り回線は 1 本分で済む（例: 6 Mbps × 5 サイト = 30 Mbps → 6 Mbps）。② スマホから「1 本送るだけ」で多重配信できる（§15.2）。③ 入力元と配信先を完全に分けられる（OBS・スマホ・ブラウザ・ファイル・別の配信を入力にできる）。
- **代償（記録しておく）**:
  - **費用は回線量で決まる。** 30 Mbps を出し続けると 1 時間で約 13.5 GB、24 時間で約 320 GB。大手クラウドの従量課金だと長時間配信では非常に高くなる。転送量込みの VPS を選ぶ前提（価格は導入時に要調査）。
  - 1 か所に集まるので、**クラウドが落ちると全サイトが同時に落ちる**（ローカルの OBS エンジンなら、1 サイトの問題は他に波及しにくい）。
  - 中継が 1 段増えるので遅延が増える。サイトごとに画質を変えるには、クラウド側で再エンコードが要る（CPU 費用が増える）。
  - 配信キーを**クラウドに置く**ことになる。金庫（DPAPI は Windows のユーザーに結び付く）はそのままでは使えないので、クラウド用の鍵管理が別に要る。
- **最初に作るなら**: 自前のサーバーを作り込む前に、既存の仕組み（自前 VPS 上の中継ソフト、または既存のマルチ配信サービス）を `stream.engine` のアダプタとしてつなぐ。Core 側は変えない。
- **見直すきっかけ**: 自宅の上り回線が足りなくなった／スマホだけで多重配信したくなった／PC を止めても配信を続けたい用途が出た。

### 15.2 スマホからの多重配信
- 原則 8（配信の実行は PC、スマホは操作端末）は**ローカル構成での原則**。クラウドの配信エンジンがある場合に限り、スマホを**入力元**として「スマホ → クラウド → 各サイト」を許す。スマホ自身が複数サイトへ送ることは引き続きしない。
- **重要な前提**: 自宅 PC を止めた状態でこれをやるなら、題名の更新・サイトのログイン・枠取りなど**Core の仕事も PC の外で動く必要がある**。つまり D8（コントロールをクラウドに置かない）を見直すことになる。その場合は、金庫・権限・ペアリングをクラウド向けに設計し直す。
- PC を動かしたままでよいなら、§12.4 の「スマホ → SRT → 自宅 OBS」で足り、クラウドは要らない。

### 15.2b 入力・配信エンジン・配信先の 3 つに分ける考え方（GPT 提案、2026-10-04 記録）
- 今は「映像を作るもの = OBS」が暗黙の前提。将来は **入力**（OBS・スマホ・カメラ・ブラウザ・ファイル・別の配信）→ **配信エンジン**（OBS エンジン・クラウド）→ **配信先**（各サイト）の 3 つに分けて考える。
- 今は入力をモデルに入れない。配信エンジンと配信先はすでに分けてある（原則 3、§4.1 の `engine`）。

### 15.3 今のうちにやっておくこと（安く済む逃げ道）
- データと API に OBS 固有の名前を持ち込まない（`engine: { id, targetId }`, `engineState`。原則 3）。
- エンジンが「何ができるか」を `capabilities` で返す（例: 配信先の作成、キーの差し替え、サイト別の画質、全部止める）。画面はそれを見てボタンを出し分ける。
- 全部止めるは「全エンジンの `stopAll`」として呼ぶ。
- これ以上（クラウドのサーバー、クラウド用の鍵管理、スマホ用の送出）は作らない。
